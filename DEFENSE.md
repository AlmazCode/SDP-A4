# Памятка для защиты

Проект — консольный подбор двух игроков для матча. Главное показать Facade, сохранение на диск и правильные откаты. Код читать в таком порядке: `App` → `MatchmakingFacade` → три подсистемы → тесты.

## Что сказать за минуту

«Моя тема — Video Game Matchmaking. Подсистема A проверяет рейтинг и резервирует пару игроков. B проверяет задержку и сохраняет выделение сервера. C проверяет результат античита и записывает подтверждённую сессию.

Клиент вызывает `startMatch` у `MatchmakingFacade`. Фасад выполняет A, B и C по порядку и сохраняет прогресс. Если B не проходит проверку задержки, фасад отменяет A. Если C отклоняет игрока, фасад сначала освобождает B, затем отменяет A.

Каждая подсистема сохраняет собственные записи в CSV. После перезапуска фасад читает журнал и реальные статусы с диска. Второй фасад, `AdminFacade`, показывает состояние и позволяет вручную отменить незавершённый матч».

## Показать преподавателю

Запуск: `./run.sh`. Вводить значения по одному, нажимая Enter. После каждого сценария пункт **2** показывает все записи.

| Сценарий | Ввод после пункта 1 | Что объяснить |
| --- | --- | --- |
| Успех | `1000`, `1100`, `50`, `n`, `0` | A RESERVED, B ALLOCATED, C CONFIRMED; цепочка COMPLETED |
| Сбой B | `1000`, `1100`, `150`, `n`, `0` | Задержка больше 100 мс; отменена только A; B и C не созданы |
| Сбой C | `1000`, `1100`, `50`, `y`, `0` | Античит отклонил игрока; порядок отката B>A; C REJECTED остаётся для истории |
| Ошибка входных данных | `-1`, `1100`, `50`, `n`, `0` | A отклоняет рейтинг; ни одна подсистема не успела сохранить операцию |
| Перезапуск | `1000`, `1100`, `50`, `n`, `1` | Скопировать ID, выйти через 0, запустить заново, показать пункт 2, продолжить через 3 и ID |
| Перезапуск перед сбоем C | `1000`, `1100`, `50`, `y`, `2` | После нового запуска пункт 3 выполняет C и откатывает B>A |
| Ручная отмена | Любой корректный матч с паузой `2` | Пункт 4 и его ID отменяют B, затем A |

Для чистого показа остановить приложение и выполнить `rm -rf data`. Тесты и отчёт покрытия: `mvn test`; отчёт находится в `target/site/jacoco/index.html`.

## Ответы на вопросы

**Где Facade?** В `MatchmakingFacade` и `AdminFacade`. Первый управляет цепочкой, второй даёт простой интерфейс просмотра и ручной отмены. В `advance` есть реальная последовательность A → B → C и обработка отказа; это не простой вызов одного метода.

**Почему не Adapter?** Adapter нужен для несовместимых интерфейсов. Здесь интерфейсы уже подходят: нужно скрыть порядок работы нескольких подсистем и их откаты. Это задача Facade.

**Почему именно четыре класса в подсистеме?** Задание требует 3–5. Здесь сущность хранит статус, отдельный класс проверяет бизнес-правило, репозиторий сохраняет данные, сервис выполняет операцию. Классы A не знают о B и C.

**Что означает независимость?** Подсистема может работать без фасада и без других подсистем. Это показано тестом `eachSubsystemCanBeUsedWithoutAnyFacade`. Общий `CsvStore` — инфраструктура чтения и записи файлов.

**Где статус и кто разрешает переходы?** В `Party`, `ServerAllocation`, `GameSession`. Методы сущностей сами проверяют переход. Например, `Party.cancel()` разрешён только из RESERVED; из NEW он выбросит `IllegalStateException` даже без фасада.

**Почему мало хранить только этап цепочки?** Программа могла сохранить B и остановиться до обновления журнала. Поэтому фасад и сервисы читают настоящие записи подсистем. Уже выполненный шаг повторно не создаётся, а при отмене проверяются фактически сохранённые A и B.

**Как доказывается порядок B, затем A?** Тест специально блокирует следующую запись A. После ошибки B уже RELEASED, а A ещё RESERVED. После исправления записи и создания нового фасада откат заканчивается. Если бы A отменялась первой, B оставался бы ALLOCATED и тест упал бы.

**Это транзакция базы данных?** Это компенсация отдельных сохранённых операций. Резервирование A отменяется статусом CANCELLED, выделение B — статусом RELEASED. Записи сохраняются для истории, а не удаляются.

**Можно ли отменить успешный матч?** Этот административный сценарий отменяет незавершённые цепочки. Подтверждённую сессию он не отменяет, даже если журнал не успел обновиться. Для отмены уже начатого матча понадобился бы другой бизнес-сценарий.

**Что при ошибке диска?** `UncheckedIOException` не выдаётся за успешно выполненный откат. Программа сообщает ошибку. После устранения причины нужно продолжить матч по ID; стадия COMPENSATING означает продолжение отката.

**Что здесь настоящий сервер и античит?** Это локальная учебная модель: выделение сервера имеет сохраняемый статус, задержка и результат проверки античита вводятся пользователем. Подключения к игровому серверу и программы поиска читов в задании нет.

**Где Principle of Least Knowledge?** В README есть собственный пример до и после. До фасада клиент создаёт и вызывает три сервиса, знает порядок и откаты. С фасадом он вызывает `startMatch` и `inspect`.

**Как соблюдается F.I.R.S.T.?** Fast — локальные файлы без сети. Independent — новая временная папка для каждого теста. Repeatable — фиксированный ввод. Self-validating — проверки JUnit. Timely — тесты находятся в Git вместе с кодом. `matchWith(...)` — небольшой DSL для тестов.

## Если попросят изменить код на месте

- Изменить допустимую задержку: `LatencyChecker.validate`, сейчас максимум 100.
- Изменить допустимую разницу рейтингов: `SkillRatingService.validate`, сейчас 300.
- Добавить правило античита: `AntiCheatScanner.validate`.
- Добавить новый отказ B: проверка в B должна выбросить `MatchmakingException`; фасад уже отменит A.
- Добавить новый отказ C до подтверждения: выбросить `MatchmakingException`; фасад уже откатит B>A.

После изменения порога обновить соответствующие граничные проверки в `SubsystemTest` и запустить `mvn test`. Не добавлять вызовы одной подсистемы из другой: координация остаётся в фасаде.
